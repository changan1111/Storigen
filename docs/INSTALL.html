Auto-ID Linker: installation and going live

Version 9.6.0 (v9.1 plus the dashboard with paging and the by-bulletin view, the report page, automatic show discovery, complete-day polling with a round deadline, and day close/open). It gives each Blaze story a clip ID, follows the file from Playout to Nitro, and says which story each finished clip belongs to. It can also attach the clip in Blaze for you, but that is off until you switch it on in section 8.

1. Before you start

  • Python 3.9 or newer (python3 --version). Nothing else to install.
  • A Blaze user made only for this tool. Treat its session cookie like a password and never put it in chat or source control.
  • Read-only access to the Playout INBOX and the Nitro folders. The program never moves, copies, renames or deletes a file there.
  • The Blaze calls used are the ones Blaze’s own web page makes. They are not vendor-documented and a Blaze update can change them. Check your support terms first.

2. Install on a Mac

  1. Copy the folder to the Mac. In Terminal inside it run: 
    ./deploy/mac/install_mac.sh you@company.com
    It creates autoid.env with fresh secrets and a launchd job, and prints the first admin password once. Write it down.
  2. Mount the shares so they appear under /Volumes/...: edit the two lines in deploy/mac/mount_shares.sh and run it. Use a read-only account for Nitro.
  3. Edit autoid.env: LINK_MODE, EXPORTS_DIR, INBOX_SUBDIRS, NITRO_DIR (see section 4).
  4. Run the checks (section 5), then start: 
    launchctl load -w ~/Library/LaunchAgents/com.autoid.lite.plist
launchctl load -w ~/Library/LaunchAgents/com.autoid.lite.restart.plist   # nightly restart at 04:30
  5. Open http://<mac-name>:8080 and sign in as the admin.
  6. Always-on Mac: run ./deploy/mac/keep_awake.sh. Automatic login is needed for the launchd job and is not available while FileVault is on. macOS may ask once to allow access to network volumes: allow it.
To restart after a settings change: launchctl unload ~/Library/LaunchAgents/com.autoid.lite.plist, then load -w again. To update the program, replace the program files and keep autoid.env and data/.

3. Install on Windows

The script is included but has not been tried on a real PC.

  1. Run deploy\windows\install_windows.ps1 in PowerShell as Administrator.
  2. Use UNC paths in autoid.env, for example \\nas\Playout\INBOX.
  3. Run the checks in section 5 with py autoid.py ... instead of python3 autoid.py ....

4. Settings that matter (autoid.env)

SettingUse
LINK_MODE=story_idIDs are made from Blaze’s own story ID. Needed for the Blaze poller.
BROADCAST_DAY_STARTThe clip ID date changes at this time (default 05:00), not at midnight.
BLAZE_POLL=1Starts the poller with the program.
BLAZE_URL, BLAZE_SESSION_ID, BLAZE_USERNAMEBlaze address, and the two cookies copied from a logged-in Blaze tab (DevTools, Application, Cookies).
BLAZE_SHOW_IDS=autoRecommended. The poller asks Blaze for the broadcast day’s shows (the same call the rundown panel makes) and follows all of them, about 36 a day. A fixed list still works: comma-separated show IDs, the number in /DataService/shows/34498/slugs.
BLAZE_CONCURRENCY=6, BLAZE_TIMEOUT_SECS=15, BLAZE_RETRY_MAX_SECS=60Complete-day polling: every show of the day is read every pass (15 s), several at a time. A show that fails keeps its last good snapshot and is retried after a growing delay, without blocking the others.
BLAZE_FRESH_SECS=15, BLAZE_STALE_SECS=90A show not read for longer than FRESH is counted as over the freshness target; longer than STALE it appears as a problem on the status pill.
BLAZE_IDENT_SECS=120, BLAZE_IDENT_BATCH=60How often each story with clips has its attachments re-read (identity sweep). See the trade-off in docs/CHANGES_v94.md.
BLAZE_RECON_BATCH=60, BLAZE_MEDIA_BATCH=40, BLAZE_INFO_SECS=60Bounds on the heavier reads per pass, so 600+ stories never stall a round.
BLAZE_CYCLE_DEADLINE_SECS, BLAZE_REQUEST_RETRIES=1, BLAZE_KEEP_COMPLETED=1, BLAZE_HOT_BEFORE_MIN=60, BLAZE_SNAPSHOT_KEEP_DAYS=14v9.5: a round waits at most the deadline (default the poll interval) for its parallel reads and never requests a slow one twice; a network or 5xx failure is retried quickly; a finished show Blaze stops listing is still followed until the day closes; old snapshots are pruned. blaze_poll.py close-day / open-day pause and resume a broadcast day.
BLAZE_SHOW_LOOKAHEAD_HOURS=5v9.5.1: shows listed under tomorrow’s date that start within this many hours and before the broadcast day ends (BROADCAST_DAY_START, default 05:00) are followed already, so a 00:00 show is not missed. 0 = off. blaze_poll.py shows lists them.
BLAZE_VERSION_MODE=deskv9.6: clips of version 2 and up (_V2…). desk: never attached by the tool, the desk is told. auto (needs live attach): attach the new clip, verify, then remove the older version’s clip with a second call; never delete first. See docs/CHANGES_v95.md.
BLAZE_SHOW_DAYS_AHEAD=0, BLAZE_IGNORE_SHOW_TITLES, BLAZE_SHOW_LIST_SECS=60Also follow tomorrow’s shows (set 1); words in a show title that make it ignored (for example TEST); how often the day’s list is asked again.
BLAZE_ATTACHoff, dry (default: log only) or live (section 8).
BLAZE_ATTACH_WHENmedia (default) logs GOING TO ATTACH once the file is in Blaze’s media list. watcher waits until the clip is on Nitro.
BLAZE_ONLY_FORMAT_IDS, BLAZE_IGNORE_TITLESWhich story formats get IDs, and which template rows (BREAK, OPEN MONTAGE) never do.
BLAZE_VERIFIED_FORMATS=20,21Story formats whose itemId rule is confirmed (20 and 21 = Anchor visual). Others are tagged CHECK and never attached live.
BLAZE_HEARTBEAT=pageThe keep-alive as the Blaze page does it: a GET on the session every minute and a PUT every 8 minutes (captured over 2.2 hours). get, put or both remain available.

5. First checks

python3 autoid.py doctor     # fix every FIX line it prints
python3 autoid.py selftest
python3 -m pytest tests      # optional, needs: pip install pytest

Commands: python3 autoid.py init | run | status | doctor | selftest | backup. Logs are in data/logs/, the database is data/autoid.db, and a copy is made daily in data/backups/ (14 kept).

6. Connect to Blaze (read-only)

Put the cookies and show IDs in autoid.env, then try each command by hand:

python3 tools/blaze_poll.py shows         # the day’s shows as Blaze lists them: id, start, title, stories, master, last read
python3 tools/blaze_poll.py show 34498    # the rundown name and its stories
python3 tools/blaze_poll.py media         # Blaze's Playout media list
python3 tools/blaze_poll.py once          # one full pass, printed, then exit
python3 tools/blaze_poll.py map           # show / slug / story / clip ID for today

If the log says PROBLEM and blaze_poll turns red on the page, the session cookie has expired. Copy fresh sessionId and username cookies into autoid.env and restart. The nightly restart only clears memory; it does not renew the cookie.

7. Watch for 5 days (dry run)

Keep BLAZE_ATTACH=dry. Nothing is sent to Blaze; the poller writes, once per clip, to the log and to data/reports/attach_watch.log:

READY ON NITRO   clip 20261107_0003J_X is on Nitro: ready for story 726521 "EXP VNR" (show 34498 ..., row 148)
GOING TO ATTACH  clip 20261107_0003J_X (file ..mxf, media 1105862, 50s) to story 726521 ... | order=149 itemId=937639 | DRY RUN: nothing sent to Blaze

Each day: read the CHECK tags and the daily CSV in data/reports/, then run:

python3 tools/blaze_poll.py summary 5

It prints, for each day, what the tool would have attached against what the desk really attached. Look for DISAGREE, TOOL_MISSED, WRONG_STORY and DUPLICATE rows.

  • 5 days on real bulletins with agreement staying clean
  • No unexplained CHECK tags, or each one understood
  • The session survived the whole time (or you know how long it lasts)

7A. The dashboard and the report page

The dashboard (story tracker)

Open http://<machine-name>:8080 and sign in. A day has 540 to 720 stories, so the list is paged (25, 50, 100 or 200 per page) and can be searched (story name, clip ID or Blaze story ID) and narrowed to one show. It shows, for the chosen broadcast day: counts (total IDs, on Nitro, needs desk, waiting, attached); a list of stories with their state, show, row, clip ID and Blaze story ID; the filters All / Action / Waiting / Done; and the buttons the desk already used (Copy ID, + Version, Open in Blaze, Mark attached). View details opens the selected story with its media file and a history: story received, Auto-ID generated, export detected, Nitro file detected, attachment verified, plus the reason when something needs the desk. The page refreshes every 5 seconds. The green or red pill at the top says whether every service (watcher, poller) is reporting.

The tool-vs-desk report page

The button Tool vs desk report on the dashboard opens it (same login). It shows the agreement percentage, the clips that need a look and why, every clip per show with what the tool would attach next to what the editor attached, and the last 5 days. /report is today and /report/20261107 a given day.

  • The poller writes the page, about once a minute while it runs, to data/reports/agreement_YYYYMMDD.html (next to the CSV). It is self-contained: you can also open the file straight from the folder or email it.
  • The web app reads the same folder. If you moved it with BLAZE_REPORT_DIR, the setting must be the same for both (it is, when both read the same autoid.env).
  • No poller running or no clips yet: the page says there is no report for that day yet.
  • While BLAZE_ATTACH=live is on, clips the tool attached itself count as AGREE, and the page says so.

8. Going live

Do not start until every box is ticked.
  • The 5-day watch in section 7 is clean.
  • Your Blaze support terms allow this tool to attach, and it uses its own Blaze user.
  • With BLAZE_SHOW_IDS=auto the show IDs change every day, so allow live by time slot: BLAZE_LIVE_MASTER_IDS=13 (the masterId in blaze_poll.py shows; 13 is the 06:30 AM bulletin) instead of BLAZE_LIVE_SHOW_IDS.
  • You have a test show in Blaze for the first live clips.
  • You know what Blaze answers to a duplicate attach and to a locked story, and the itemId for any format beyond Anchor you intend to use. Until then keep BLAZE_VERIFIED_FORMATS=20.

What live does

For a clip it attaches once, and only when all of these hold: its show is in BLAZE_LIVE_SHOW_IDS; the clip is on Nitro; exactly one settled file matches in Blaze; the story format is verified; there is no CHECK tag (so no linked story); the kill-switch file is absent; the hourly limit is not reached. The attempt is written to the ledger before the call, so a clip is never sent twice, not even after a crash. Afterwards the story is read back and must show exactly one new clip with that file. Anything else goes to the desk as NEEDS_DESK with the reason, and is not tried again by itself. After 3 failures in a row live stops by itself.

Switch it on, step by step

  1. Stop the program (section 2, unload).
  2. In autoid.env set all three together, with the test show only: 
    BLAZE_ATTACH=live
BLAZE_LIVE_MASTER_IDS=<test slot>        # with BLAZE_SHOW_IDS=auto; or BLAZE_LIVE_SHOW_IDS=<show id> with a fixed list
BLAZE_LIVE_CONFIRM=YES_ATTACH_FOR_REAL
    With any of the three missing, the poller refuses to start and says which.
  3. Start the program. The first line should say attach=live LIVE for shows .... Check: 
    python3 tools/blaze_poll.py live
  4. Export one clip for a story in the test show. Expect READY ON NITRO, then GOING TO ATTACH ... LIVE: sending now, ATTACHING and ATTACHED.
  5. Open that story in Blaze and check: the clip is there once, in the right place, with the right duration. The page also sends a scriptDur update after an attach; this tool does not, so check the duration of stories with script text.
  6. If anything is wrong, undo (section 9). If it is right, repeat with a few more clips before widening.
  7. To widen, add show IDs to BLAZE_LIVE_SHOW_IDS one at a time and restart.

9. Stopping, undoing, rolling back

You want toDo this
Stop all sending at once, no restartCreate the file data/STOP_LIVE. While it exists nothing is sent. Delete it to resume. Live also creates it by itself after 3 failures in a row (LIVE HALTED).
Go back to log-onlySet BLAZE_ATTACH=dry and restart.
See what live didpython3 tools/blaze_poll.py live (switches, kill switch, sent in the last hour, last attempts).
Remove a clip the tool attachedpython3 tools/blaze_poll.py undo <clip ID>. If the read-back found several new clips, add the Blaze clip ID it listed: undo <clip ID> <blazeClipId>. Then check the story duration in Blaze.
Let a failed clip be tried once moreFix the cause, then python3 tools/blaze_poll.py live-retry <clip ID>. The clip must be ON_NITRO again.

The desk can always attach by hand and press Mark attached; Auto-ID reads Blaze back and notices.

10. Reading the log

LineMeaning
READY ON NITROThe clip is on Nitro. It names the story it belongs to.
GOING TO ATTACHThe plan, with order, itemId and the exact POST. Ends with DRY RUN, LIVE: sending now or NOT SENT (live blocked: reason).
| CHECK: ...Something is unconfirmed: unverified story format, no script item, unknown row, or the story is linked in several shows. Never sent live.
ALREADY IN STORYThe file is already attached there. Nothing to do.
AMBIGUOUSTwo Blaze files carry the ID. The desk chooses.
ATTACHING / ATTACHEDLive: sent, then confirmed by reading the story back (with Blaze’s clip ID).
ATTACH FAILEDLive: Blaze refused, or the read-back did not match. The clip is NEEDS_DESK with the reason on the page.
LIVE HALTEDToo many failures in a row. Delete data/STOP_LIVE after fixing the cause.
PROBLEM: ...Usually an expired Blaze session cookie. Renew it (section 6).

11. Still open

  • The reply to an expired session, and how long a session lives. The login call is known (POST /sessions, user and password) but the cookies it sets were not in the capture, so the cookie is still renewed by hand.
  • itemId for Package and Montage stories (Anchor visual, format 21, is confirmed).
  • The scriptDur rule for stories that already have script text. For a story whose script time is just its clips, it is set the way the page does; otherwise it is left alone and logged.
  • Blaze’s replies to a duplicate attach and to a locked story, and how the media title search matches.

Remove staff names, user IDs, session IDs and cookies from anything you send for help.
